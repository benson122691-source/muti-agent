# 程式導讀

這份文件帶你讀懂整個專案。全部程式碼約 1,900 行，照下面的順序讀，大約 2 到 3 小時可以讀完。

## 1. 先看一次查核走過哪些程式

使用者在網頁按下「開始查核」（V3）之後：

1. `web/index.html` 的 `submitCheck()` 把文字送到 `POST /api/check`
2. `api/main.py` 的 `api_check()` 決定版本（沒有金鑰或超過每日上限就降級成 V0），呼叫 `check()`
3. `agents/pipeline.py` 的 `check()` 建立一份 `Trace`，進入 `run_multi(review=True)`
4. `_route()`：分流 agent 判斷類型；程式再用規則確認訊息裡有沒有網址
5. `_pick_checkers()`：決定要跑哪些查核 agent（沒有網址就不跑連結查核）
6. `_run_checkers()`：用 `asyncio.gather` **同時**跑多個查核 agent
7. 每個查核 agent 都是 `agent_loop.py` 的 `Agent.run()`：呼叫模型 → 執行工具 → 再呼叫模型……直到提交 `Finding`
8. `_aggregate()`：彙整 agent 讀所有 findings，產生報告的結論
9. 審查 agent 檢查報告；不通過就重查被點名的 agent，再彙整一次（最多 1 次）
10. `Trace.save()` 把整個過程存到 `logs/traces/<trace_id>.jsonl`（已遮罩個資）
11. API 回傳報告，網頁顯示結果

```text
│   ├── definitions.py   組裝各個 agent

├── ml/                  話術分類器

```

## 4. 想改什麼，去哪裡改

| 想做的事 | 要改的地方 |
| --- | --- |
| 調整某個 agent 的判斷規則 | `agents/prompts.py` |
| 換模型、改步數上限、改每日上限 | `config.py` 或 `.env` |
| 新增一種操弄手法的關鍵字 | `ml/classifier.py` 的 `TACTIC_PATTERNS` |
| 新增一個工具 | 在 `tools/` 寫函式 → 在 `agents/definitions.py` 的 `TOOLS` 登記 → 加到某個 agent 的工具清單 |
| 新增一個查核 agent | `prompts.py` 寫 prompt → `definitions.py` 的 `make_checkers()` 加一個 → `pipeline.py` 的 `_pick_checkers()` 決定何時啟動 |
| 改風險等級的規則 | 彙整 agent 的 prompt（`AGGREGATOR`）；V0 的門檻在 `config.py` |
| 改網頁外觀 | `web/index.html` |

## 5. 正式使用前，要換掉的合成資料

目前 `data/seed/` 和 `evals/sample_testset.jsonl` 都是手寫的合成資料，只是讓程式能跑。正式使用前要換成真實資料：

- [ ] **黑名單：** 到 data.gov.tw 複製 165 資料集的 CSV 下載連結，填入 `.env`，執行 `python -m crawlers.update_data`
- [ ] **合法業者名單：** 從投信投顧公會網站整理成 `data/raw/licensed.csv`（一個欄位：名稱）
- [ ] **訓練資料：** 收集並標註真實訊息，格式同 `data/seed/train_seed.jsonl`，執行 `python -m ml.train --data 你的檔案`
- [ ] **案例庫：** 整理 165 闢謠專區、宣導資料，格式同 `data/seed/cases_seed.jsonl`
- [ ] **測試集：** 200 筆真實資料，切成開發集和保留集（保留集最後才跑一次）

## 6. 怎麼除錯：讀 trace 檔

每次查核都會產生 `logs/traces/<trace_id>.jsonl`，網頁回傳的 `trace_id` 就是檔名。一行是一個事件：

```json
{"t": 1.23, "agent": "link_checker", "kind": "tool_call", "data": {"tool": "check_blacklist", "input": {"domain": "xxx.com"}}}
```

- `t`：從查核開始過了幾秒，可以看出哪個 agent 最慢
- `kind`：`llm_call`（呼叫模型）、`tool_call`、`tool_result`、`output`（提交結果）、`error`

判斷錯誤時，照這個順序找原因：

1. 分流有沒有判斷錯，導致該跑的 agent 沒跑？看 `routing` 事件
2. 某個 agent 有沒有呼叫錯工具，或少呼叫工具？看它的 `tool_call`
3. 工具回傳的資料對不對？看 `tool_result`
4. 資料都對，但結論錯？那就是 prompt 的問題，去改 `prompts.py`

改完之後重跑評估，確認分數有變好、其他案例沒有變差。

## 7. 讀完之後的練習

做完這三題，就代表你真的懂這套程式了：

1. **加一種手法：** 在 `TACTIC_PATTERNS` 加上「假冒客服」（例如：客服、解除分期、ATM 操作），再寫一個測試確認抓得到。
2. **加一個工具：** 寫 `check_phone_format(text)`，檢查訊息裡有沒有 +886 以外的國際電話，把它給身分查核 agent 用。
3. **加一個 agent：** 做一個「QR code 查核」agent 的骨架（工具先回傳假資料），讓分流 agent 在訊息提到 QR code 時啟動它，並在 `test_pipeline.py` 用 FakeLLM 寫一個測試。
